# chat-service → 内部知识助手

一个带工具调用、多步 agent 循环、流式输出和量化评估的 LLM 应用骨架。

从「能对话」长到「能查资料、能算数、能自我纠错、可被度量」，每个阶段都有对应的评估数字。
仓库名沿用 `chat-service`，实际形态是逐步长成的 agent 服务。

## 它能做什么

| 能力 | 说明 |
|---|---|
| **多轮对话** | 带历史上下文，可连续追问 |
| **流式输出** | SSE 逐块返回，首字节延迟从 ~2s 降到 <0.5s |
| **工具调用** | 三个工具：查时间、算数学、**检索内部知识库**（BGE 向量检索 + 阈值拒答）；模型自主决定调哪个 |
| **多步 agent 循环** | 连续决策 → 执行 → 观察，带步数上限、循环检测、兜底强制回答 |
| **可观测** | 每步记录工具、参数、结果、LLM/工具耗时；结构化 JSON 日志 + request ref |
| **可评估** | 15 条固定用例，一条命令算出通过率、成本、延迟 |
| **可做对照实验** | 提示词变体可热切换，配合固定评估集量化「改动到底有没有用」 |

## 接口

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/healthz` | 存活探针 |
| GET | `/config` | 查看当前生效配置（不回显密钥） |
| POST | `/chat` | 单轮对话（含多轮历史） |
| POST | `/chat/stream` | 流式对话（SSE） |
| POST | `/chat/tools` | 单步工具调用 |
| POST | `/agent` | 多步 agent 循环，返回完整执行轨迹 |
| GET | `/docs` | Swagger 自动文档 |

## 配置项

所有配置走 `.env`（`config.py` 里的同名属性只是默认值）。

| 变量 | 默认 | 作用 |
|---|---|---|
| `DEEPSEEK_API_KEY` | 无（**必填**） | 服务商密钥，缺失则启动失败 |
| `DEEPSEEK_BASE_URL` | `https://api.deepseek.com` | OpenAI 兼容接口地址 |
| `MODEL_NAME` | `deepseek-flash` | 调用的模型，**以 `list_models.py` 实际返回为准** |
| `REQUEST_TIMEOUT` | 30 | 单次请求超时（秒） |
| `MAX_RETRIES` | 2 | SDK 层重试次数（只重试可重试类错误） |
| `TEMPERATURE` | 0.0 | 输出随机性。0 = 每次都取最高概率词（评估用）；生产问答可 0–0.3，创意类 0.7–1.0 |
| `MAX_OUTPUT_TOKENS` | 0 | **0 = 不限制**，交给服务商默认上限；设正数则硬性截断输出 |
| `PROMPT_VARIANT` | on | on = 注入默认系统提示；off = 不注入（用于 A/B 对照） |
| `INPUT_PRICE_PER_1M` / `OUTPUT_PRICE_PER_1M` | 0 | 成本估算单价（元 / 百万 token），从服务商定价页取当时数值 |

优先级：**操作系统环境变量 > `.env` 文件 > `config.py` 默认值**。

## 架构

```
app/
├── main.py      HTTP 层：路由、异常处理器。不含业务逻辑
├── agent.py     业务层：agent 循环、停止条件、执行轨迹
├── llm.py       模型层：同步/异步客户端、成本估算、流式
├── tools.py     工具层：实现 + 给模型看的说明书 + 统一执行入口
├── rag.py       检索层：文档切分 → 向量化 → 余弦召回 → 阈值拒答
├── prompts.py   提示词层：版本化系统提示 + 变体开关
├── schemas.py   契约层：请求/响应/轨迹的 pydantic 模型
├── config.py    配置：从环境变量加载，缺失即启动失败
├── errors.py    错误：分层异常 + 脱敏 + request ref
└── logs.py      日志：结构化 JSON，同时写终端和滚动文件
```

**分层的判断标准**：换成别的 Web 框架，`agent.py` 一行都不用改；换成别的模型服务商，`llm.py` 一行。如果一次改动需要动三个文件，说明分层漏了。

**数据与索引**

```
data/
├── docs/     语料：markdown，# 是文档、## 二级标题是片段边界 —— 进仓库
└── index/    vectors.npy + chunks.json + corpus.fingerprint —— 可重建，不进仓库
```

改完 `data/docs/` 不需要手动重建：索引带语料指纹，不一致时下次检索自动重建。

## 几个刻意的设计决策

1. **错误两段式**：服务端日志存完整堆栈 + `ref`，客户端只拿到「脱敏文案 + ref」。工具异常也转成模型可读的文本回灌，而不是抛出——否则一个参数错误就让整个请求 500，而且模型失去了自我纠正的机会。
2. **不可信输入在工具层拦截**：`calculate` 不用 `eval`，而是解析语法树只允许数字与四则运算；指数做上限检查，防止 `2 ** 999999` 这类资源耗尽。
3. **配置缺失即启动失败**：`Settings` 里 key 没有默认值，缺了服务根本起不来，而不是等到第一笔真实请求才报错。
4. **流式错误走流内事件**：HTTP 头一旦发出就无法改状态码，所以错误作为一条 `{"type":"error","ref":...}` 事件下发。
5. **失败也要可定位**：每个异常带 8 位 `ref`，用户在日志里一搜就能定位到那一次请求的完整堆栈。
6. **提示词是可版本化的资产**：`prompts.py` 带 `PROMPT_VERSION`，变体可开关，每次改动都要过评估集。

## 评估结果

15 条固定用例（14 条自动判定 + 1 条需人工），覆盖单工具、多步串联、拒答、工具失败、指令遵循、过度调用。
口径统一：`Temperature=0`，`--repeat 2`。

| 指标 | v1（对照） | v2（当前） |
|---|---|---|
| 自动通过率 | 26/28 = 93% | 25/28 = 89% ※ |
| 每轮成本 | 0.0635 元 | 0.0588 元 |
| 平均延迟 | 1725 ms | 1502 ms |
| 平均输出字数 | 158 字 | 103 字 |

※ 两轮分别为 11/14 与 14/14；差距来自 c05 / c09 / c12 三条的轮次抖动。28 次判定里只差 1 次，属噪声范围，**不能据此判断 v2 更差**。

### 检索方式对照（v2 → v3，当前）

| 指标 | v2（关键词） | v3（向量） | 变化 |
|---|---|---|---|
| c11 工具调用次数 | 4 | **1** | −75% |
| c13 工具调用次数 | 4 | **1** | −75% |
| c13 单条成本 | 0.0110 元 | **0.0069 元** | −37% |
| c13 延迟 | 7.3 s | **3.5 s** | −52% |
| 每轮成本 | 0.0709 元 | 0.061–0.063 元 | −13% |
| 平均延迟 | 1656 / 1793 ms | 1295 / 1253 ms | −25% |
| 平均输出字数 | 152 / 163 字 | 105 字 | −34% |
| 自动通过率 | 26/28 = 93% | 26/28 = 93% | 持平 |

※ 两轮为 12/14 与 14/14。修复索引与用例后，剩余抖动集中在年假类（c03 / c11 各翻 1 次），根因是**模型自由改写检索查询**，命中分数在阈值 0.60 附近摆动（实测同一问题改写不同：0.774 命中 / 压线 0.634）。属已知边界，计划在 W4 用混合召回 + rerank + 固定检索参数收敛。

分档单次成本（v2）：

| 请求类型 | 成本 | 延迟 |
|---|---|---|
| 纯对话（无工具） | 0.001-0.002 元 | <1s |
| 单工具 | 0.003-0.005 元 | 1.5-2.5s |
| 多步（2-3 工具） | 0.006-0.009 元 | 2-3.5s |
| 长回答（优化前 >1000 字） | 0.012-0.022 元 → 优化后约 0.006 元 | 7-13s → 约 2.3s |

复现：

```powershell
.\.venv\Scripts\python.exe -m eval.run_eval             # 全量
.\.venv\Scripts\python.exe -m eval.run_eval --case c13  # 单条
.\.venv\Scripts\python.exe -m eval.run_eval --repeat 3  # 多轮测稳定性
```

报告写入 `eval/report-<时间戳>.md`，头部记录变体/温度/模型，正文含每条的执行轨迹与完整回答。

## 优化记录

### v3：关键词检索 → 向量检索

改动：新增 `app/rag.py`（按二级标题切分 → BGE-small-zh 嵌入 → 余弦检索），`search_kb` 换成调它，**工具描述与入参 schema 一个字没改**（模型侧零改动，因为工具是接口、检索是实现）。

语料 3 份 markdown、25 个片段（含 4-6 个干扰主题）；阈值 `MIN_SCORE=0.60`，取「正例最低 0.687 / 负例最高 0.508」的中点，让两侧容错均衡。

| 指标 | 关键词 | 向量 |
|---|---|---|
| c11 工具调用 | 4 次 | 1 次 |
| c13 工具调用 | 4 次 | 1 次 |
| c13 单条成本 | 0.0110 元 | 0.0069 元 |
| c13 延迟 | 7.3 s | 3.5 s |
| 每轮成本 | 0.0709 元 | ~0.062 元 |

**动机链（本仓库最连贯的一条证据线）**：D8 用评估集发现「弱检索导致模型反复换词重试，c11/c13 各调 4 次」→ W3 换成向量检索 → 用同一把尺子证明重复调用消失、成本降 37%。**先有问题数字，再有修复，最后有验证**，而不是"换了个更时髦的方案"。

**副作用（与检索方式无关，但同时被暴露）**：

- **c04 失败源于索引过期**：语料新增了「报销提交时限」，但索引缓存里没有这一条，正确片段**根本没进入检索范围**（探针里 top-5 都看不到它）。修法是给索引加语料指纹，指纹不一致就自动重建——把"人记得重建"变成"系统自己发现过期"。
- **c12 用例规定过死**：模型对「3 除以 0」选择不调工具、直接讲数学，回答正确且未泄漏 `ZeroDivisionError`，但用例的 `expect_tools` 强制要求必须调用 `calculate`。**路径类断言应放在单元测试里，评估集只判用户可观察的结果。**

### v2：约束输出长度与重复工具调用

改动：系统提示加篇幅与工具使用约束；`search_kb` 描述加「每次对话最多调用一次」。

**全量层面无可测差异**（成本差 0.0047 元、通过率差 1 次判定，均在噪声内）。
差异集中在「长回答」类用例：

```
全量成本差    0.0635 − 0.0588 = 0.0047 元
c13 单条成本差 0.0110 − 0.0066 = 0.0044 元
```

两个数字几乎相等 —— **整集平均的改善几乎全部来自一条用例**。其余 13 条本来就是短回答，没什么可压缩的。

### 2×2 对照（c13，各 3 轮，中位数）

| | 原工具描述 | 新工具描述 |
|---|---|---|
| **无系统提示** | 0.0110 元 / 784 字 / 通过 1-3 | 0.0080 元 / 482 字 / 通过 2-3 |
| **有系统提示** | 0.0060 元 / 217 字 / 通过 2-3 | 0.0066 元 / 160 字 / **通过 3-3** |

| 效应 | 条件 | 成本变化 |
|---|---|---|
| 系统提示 | 原工具描述 | **−45.6%** |
| 系统提示 | 新工具描述 | −17.6% |
| 工具描述 | 无系统提示 | −27.3% |
| 工具描述 | 有系统提示 | **+10.0%** |

**结论：两个约束部分冗余。** 两处都在说「别重复调工具」，同时开启时工具描述那句不再带来新信息，只多占约 40 token/轮。

保留工具描述那句的理由不是收益，而是**兜底**：客户端传入自定义 `system_prompt` 时会覆盖默认系统提示，那时工具描述里的约束还在。

## 已知限制

| 限制 | 影响 | 计划 |
|---|---|---|
| 极短的关键词式查询得分偏低 | `"年假"` 只有 0.595，刚好卡在阈值 0.60 之下被拒答；用户真的会只搜两个字 | **W4 混合召回（BM25 + 向量）**——BM25 对短关键词极强，与向量互补；测试里已用 `xfail(strict=True)` 锁住该弱点 |
| 检索参数 `top_k` 暴露给模型，且模型会自行改写查询 | 同一问题不同轮次可能改写为不同查询，命中分数在阈值附近翻转（c03 / c11 各 1 次） | W4：`top_k` 收归服务端固定；考虑 multi-query 把改写变成受控步骤 |
| 只有单一向量召回，无混合召回与重排 | 区分度窗口窄（正例最低 0.687 / 负例最高 0.508），语料主题变杂后相近主题会互相挤压 | W4 加 BM25 混合召回 + rerank |
| `calculate` 不支持日期运算 | 涉及「多少天后」的问题只能靠模型心算 | 视需求补 `add_days` 工具 |
| 部分用例存在轮次抖动（c05 多步、c12 工具报错） | 单轮结论不可靠，需 `--repeat` | 逐条复查，抖动项改用单元测试锁定 |
| 优化只在特定用例类型上可测 | 整集平均容易掩盖单条差异 | 评估报告保留逐条数据，按用例类型分组看 |
| temperature=0 也不保证完全确定 | 极端情况下仍可能出现不同工具序列 | 结论一律看区间与多轮，不看单次 |
